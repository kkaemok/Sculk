## Authentication blocker and next step

The older Rust/TypeScript implementations describe private login APIs with device
identity and version-sensitive headers. Recent openkakao-cli reports that its login
and new-device paths fail; its current useful automation uses a logged-in macOS
application. That cannot meet the native headless Linux requirement.

To unblock milestone 3, establish an authorized test account and legitimate current
device verification/login procedure with documentation or sanitized reproducible
traces, a trustworthy server key/negotiation route, platform/version, and expiry /
error behavior. Review those before any live test. Do not send account secrets to
chat or commit them. Tests in public CI never contact KakaoTalk.

An active-member kick and editing a server's departed-member kicked list remain
separate operations. Neither historical KICKOUT packets nor a persistent local
blocklist prove the latter exists. Profile changes may change visible identity;
a bot must not equate a room-specific profile with a stable account.

## Phase 2 live-test status — 2026-10-25

No Kakao credential binding or KAKAO/SCULK credential variable was found by
name/presence checks. No values were inspected, and no live login was attempted.
The public sources still document broken recent device-login flows. Sculk now
has verified-TLS infrastructure and a provider-driven lifecycle; it has no
built-in current provider, production LOGINLIST builder or endpoint dialer.

The smallest next step is an authorized, human-observed validation of a current
account/device flow and the exact endpoint certificate identity and client
profile. Then implement that specific provider and test the minimum session
acknowledgment. Existing historical request differences and alternative hostname
verification in openkakao-cli must be resolved explicitly, not copied as defaults.

## Phase 3 status — 2026-10-25

`protocol-connect` implements the initial source-profile sequence, including
RSA/GCM key setup and initial LOGINLIST, using already-authorized credentials.
The native implementation does not require Agent Messenger, Bun, Node or an
installed KakaoTalk application. No account/device login provider or registration
operation has been added. Any future device registration requires explicit user
approval and legitimate device confirmation; a -100 result is not permission to
register or repeatedly retry automatically.

Source agreement is not live proof: Agent's protocol knowledge derives in part
from OpenKakao, and their selected transport routes and Booking fields differ.
Protection is explicit per Checkin/chat stage. TLS is never silently swapped
for LOCO GCM or verified under an alternate hostname. The source-derived test
RSA key is not an automatically trusted production identity. CHECKIN account
IDs are encoded as Int64 instead of the reference's JS Number; this avoids
precision loss but remains a live-compatibility assumption.

No live account was explicitly authorized, so none was contacted. To proceed,
obtain a legitimately approved LOCO-capable token, its actual device UUID,
provider-consistent profile, documented expiration, trusted server-key/endpoint
identity, and a permitted network dialer. Run only a minimal authorized connection
and acknowledgment test first. After that, validate the smallest read-only room
lookup and a single explicitly authorized text send; no message is sent by this
milestone and no automatic send retry is provided.

## Phase 4 status — 2026-10-25

A concrete Android HTTP provider now exists; earlier phase statements that no
provider was implemented describe the historical state. The code actually builds
and sends the source-backed login/challenge/register/refresh requests when an
application explicitly invokes them. It uses fixed HTTPS origin, normal TLS,
no redirects/retries and bounded state transitions. The example joins this provider
to the existing real native protocol path. This does not prove current service
acceptance: all executed server requests used isolated local test servers.

User ID 9007199254740993 (beyond JS safe integer range) is tested from HTTP response
through BSON Int64 CHECKIN and final LOGINLIST identity. Registration approval,
rejected credentials/registration, token rotation/expiry, changed endpoints,
encryption/partial packet failures, timeout/cancellation and cleanup are covered.
Credentials are memory-only; only device UUID is stored privately. Automatic
refresh, forced login, registration without approval, Mac/Windows account HTTP
providers and credential persistence remain unsupported.

Current live blockers are an explicitly authorized test account with known numeric
ID, accepted sub-device profile and device confirmation, independently trusted
server-key identity and approved HTTPS/raw-TCP routes. Follow authentication.md;
do not paste secrets in chat or assume synthetic fixtures are live captures.

## Phase 5 readiness — 2026-10-26

The CLI now requires an independently checked RSA fingerprint, supports a network-
free --dry-run, emits static phase labels, writes owner-private sanitized reports,
and cancels device-consent input without a stuck blocking thread. Password and
superseded token lifetimes are shorter. TLS name/certificate verification and
explicit no-downgrade/no-forced-session rules remain intact.

Source-backed read-only LCHATLIST/CHATINFO/GETMEM subsets are implemented and
fixture-tested; none has been live-tested. High IDs remain exact, mismatching
room IDs and non-progressing pagination fail, missing fields are not fabricated,
and unconfirmed/expired sessions cannot make requests. The optional CLI read step
prints counts only. Automatic pagination, full membership synchronization,
room title interpretation, message history, read marks and mutation are unsupported.

No owner-approved live credentials/phone workflow was provided. No real account
connection was attempted. The owner procedure in authentication.md, with a verified
pin/profile and approved HTTPS/raw TCP routes, is the remaining next step. Uploading
source to GitHub does not establish live authentication or production readiness.
